1. 何を作るか

画像と動画の素材を取り込み、意味（セマンティック）で探し、 詳細とプレビューまで到達できるサーバーです。

いちばん見せたい体験（Feature 001）

「屋外で笑っている女性」のような自然言語クエリで、 画像も動画も混在した素材一覧が返り、クリックすると原素材を見られる。

本番の置き場所は GCP。ただし最初の開発は GCP なしでローカル完結。 クラウドの都合でドメイン設計を歪めない、が大原則です。

3. 処理パイプライン（ここが本体）

素材が検索可能になるまで、だいたい次の順番で処理が進みます。 「検索」は最後の段で、前段の成果物（メタデータとベクトル）を使います。

01

指定ディレクトリから Import

例: data/incoming/ を一括取り込み。 監視（watch）は必須ではない。
対応保証: JPEG / PNG / MP4(H.264)。それ以外は SKIP + 警告して続行。

02

Identity（同一判定）

資産の ID = import root からの相対パス。再 import は upsert（増殖しない）。 中身の hash を Domain の identity にはしない。

03

Metadata 抽出

自動: MIME, size, 幅高さ, duration, EXIF, ffprobe 系。
人手/fixture: tags, description。AI キャプションは作らない （Embedding 品質と混ぜて評価しないため）。

04

動画だけ：代表フレーム抽出

動画を数枚の静止画に落とす（後述）。画像はそのまま 1 枚として次へ。 音声・字幕・シーン検出はしない。

05

Embedding（ベクトル化）

画像（と動画の各フレーム）を数値ベクトルにする。 検索クエリのテキストも同じ空間のベクトルにする （いわゆる multimodal / CLIP 級が必要）。
Fake 配線・決定的テスト用　 Real Local 意味検索の本番評価用

06

Local Vector Index へ保存

局所・単一ランタイムの既存エンジンへ格納（ANN 自作はしない）。 managed な大規模 Vector infra（Vertex AI Vector Search など）は 001 では使わない。

07

検索

ユーザーの自然言語クエリを embed → 近いベクトルを取る → mediaType / tags で絞る → MediaAsset 一覧（スコア・サムネ）。

08

詳細 & Preview

詳細画面。原素材はパスを生で見せるのではなく、 MediaSource Port → HTTP で画像表示 / 動画再生。

一文フロー
incoming/
  → import / upsert
  → metadata
  → (video → frames)
  → embed
  → local vector index
  → semantic query + filters
  → MediaAsset results
  → detail + HTTP preview

4. 動画の扱い（崩壊＝collapse）

動画も画像も同じ埋め込み空間に載せます。 ただしユーザーに返す単位は常に「素材 1 件（MediaAsset）」です。 「フレームがヒットした」ことを Domain の検索結果型にはしません。 

Video
  ├ duration < 5s  → 中央フレーム 1 枚
  └ duration ≥ 5s  → 最大 3 枚を均等サンプリング
        │
        ▼
   frame embeddings（画像と同じ空間）
        │
        ▼
   score = max(frame scores)
   bestFrame = 最高スコアのフレーム（証跡・サムネ用）
        │
        ▼
   検索結果には Video Asset が 1 件だけ並ぶ
  • 一覧 Asset / mediaType / score / thumbnail（動画は bestFrame 由来）
  • 詳細 bestFrame を optional で見せてよい（デバッグ証跡）
  • 禁止 VideoSegment を Domain の検索ヒットとして公開

5. 検索の契約

001 の検索はこれだけです。キーワード検索という言葉は使いません。

query（必須・空文字は 400）
  ↓
semantic search
  +
metadata filters
  · mediaType: image | video
  · tags: 複数指定時は AND
  ↓
results（融合ランキングはしない）
やること やらないこと（001）
意味検索が主 filename / path / description の部分一致
tags の AND 絞り込み OR や複雑な条件式
空クエリはエラー filter だけのブラウズ一覧
画像＋動画の混在結果 スコア融合（keyword×semantic など）

合格の測り方（semantic）

  • 小さな golden set（8〜12 クエリ）。画像・動画の両方を含む。
  • 機械: expectedAssetId ∈ Top-5（Real Local Embedder）
  • 人間: Outer で「使えそうか」
  • Fake Embedder では意味検索 PASS にしない

7. Vertex AI Vector Search について

結論（確定方針との整合）

001 の主エンジンには使わない。 公式サポートがあることと、Local-first の第一スライスは別問題です。

  • 001 禁止事項: managed / distributed 大規模 vector infrastructure
  • 001 要件: GCP 認証なしで意味検索 AC を通す
  • 切り分け: 「検索が悪い」のか「GCP 化で壊れた」のかを分けたい
002 での扱い

Vertex AI Vector Search は 002 の有力候補になり得る。 ただし正式選定は 001 収束後。今は「候補メモ」まで。 

001  LocalVectorSearch（例: SQLite + sqlite-vec 等）
        ↑ 同じ VectorSearch Port
002  GcpVectorSearch（中身が Vertex でもよい）

8. 完了の測り方（ゲート）

Default verify
  · unit / Fake wiring / import / API など決定的なもの
  · 巨大モデル取得は背負わない

Semantic-real gate（別コマンド/ジョブだが 001 では必須）
  · Real Local Embedder
  · 固定 model/version
  · golden Top-K
  · モデル取得失敗 → FAIL（黙って SKIP しない）

+ full profile の reviews
= 001 converged

認証なし・単一ユーザー。AuthPort すら 001 では作らない。
